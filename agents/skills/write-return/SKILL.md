# write-return — 如实汇报结构

每张任务卡收尾(完成 / 部分完成 / 中止 / BLOCK)都按此结构汇报。**汇报的价值在于可核对,
不在于好看。**

## 结构(按序)

1. **一句话结论**:完成 / 部分完成(完成了什么没完成什么)/ 中止(停在哪)。
2. **做了什么**:动作级清单(不是感想)。
3. **改动清单**:文件路径 + 改动性质;有 commit 则附 hash。
4. **测试/验证结果原文**:命令 + 输出摘录,**引原文不转述**;没跑就写没跑、为什么没跑。
5. **排除物 + 理由**:决定不做/不提交的东西,逐项说明。
6. **异常与自作判断**:何处偏离了卡、依据什么判断、影响面。
7. **实际使用的模型 + 自报 token 用量**(能力账本进料,格式:`model=<provider/model>,
   tokens≈<in/out>`;多模型分段报)。**模型字段必须抄运行时指示**(harness 状态栏显示的
   模型名 / 驱动方启动本会话时指定的模型),**禁止凭自我认知填写**——模型对自身身份的
   感知不可靠(实案 2026-07-24:会话自报的模型名被 session 记录证伪)。
8. **待办 / 未做项**:留给驱动方(顾问 / Owner / 审计)的明确事项与未完成项,逐条列出,
   不写下一步命令。

## 落点与收尾

- 报告**写到卡面声明的落点**(卡面「报告落点」给出的绝对路径),不自选位置、不另存副本。
- **写完即止**:认领、派审、裁决、finalize、push、deploy 都由驱动方经产品完成,
  报告里不教、不代做、不写这些动作的命令;报告落盘后本角色的工作即结束。

## 红线

- 失败如实报;禁止"应该没问题/大概率成功"这类不可核对表述。
- 测试输出与数字必须可复核;粉饰 = 事故。
- 不写入任何治理档/台账——唯一写出口 = 卡面声明的报告落点,其余落笔归驱动方。
