# card-author — 顾问出卡检查表

**角色**:advisor(顾问)专用。executor/auditor 不需要此 skill(他们只执行已出好的卡)。

## 为什么(长期有效)

**问题源**:顾问出卡质量直接决定执行体能否零阻塞独立完成。历史痛点:
- **单卡多靶/贪大**:一张卡塞5个不相关靶点 → executor 无法原子交付,部分完成 = 审计噩梦。
- **验证+修复混装**:「修bug + 验证修复是否生效」塞一卡 → executor 改完无验收标准,顾问
  还得人肉复查 = 零人肉链断点。
- **上下文爆炸**:卡内知识入口指向整个产品仓 → executor 冷启动读半小时,token 预算耗尽还没动手。

**长期有效性**:卡是任务原子、审计单元、能力账本的最小粒度;出卡纪律 = 系统设计权威的
第一道防线。链路/模型再升级,原子性、可验收性、上下文预算的基本约束不变。

## 检查表(出卡前逐项自查)

### ✅ 单卡单靶(或同族靶≤3)
- [ ] 本卡只解决**一个**明确问题,或同机制的一小族靶点(例:三个假成功的同类 bug)。
- [ ] 如果卡内靶点 >3,是否可以拆成独立的多张卡?(独立 = 可以分开验收、分开审计)
- [ ] **反例**:「修复登录 bug + 重构配置模块 + 优化数据库查询」→ 三不相关,拆三张卡。
- [ ] **正例**:「修复批六靶——R6D坐实三洞根治」(同源设计缺陷,一次性修)。

### ✅ 交付大项 ≤3
- [ ] `artifact_scope` 声明的交付大项 ≤3 个(大项 = 独立可验收的产出单元)。
- [ ] 如果 >3,是否说明本卡范围过大?能否聚焦到核心 1-2 项,其余另出卡?
- [ ] **N0 容量 lint**:draft_publish 会自动 WARN,但出卡前自查更高效。
- [ ] **反例**:`artifact_scope: 功能A + 功能B + 功能C + 功能D + 清账 + 文档` → 6项,必拆。
- [ ] **正例**:`artifact_scope: 修复部署分支强制 + 添加契约测试` → 2项核心交付。

### ✅ 验证、修复、清账不混装
- [ ] 本卡是纯**验证卡**(测试/巡检/确认现状)、纯**修复卡**(改代码/配置)、或纯**清账卡**(收尾/归档)?
- [ ] **禁混装**:「修bug + 验证修复是否生效」→ 拆两张卡(修复卡 → 验证卡,后者依赖前者)。
- [ ] **原理**:修复的验收标准 = 代码改完 + 通过测试;「验证修复是否生效」= 另一层巡检,
  属独立验收点 → 独立卡,executor 才能原子交付。
- [ ] **反例**:`artifact_scope: 修复批六靶 + 验证修复 + 收尾另卡R6F` → 修复 ≠ 验证 ≠ 收尾,必拆。
- [ ] **正例**:本卡(R6E)= 纯修复批;验证收账另出卡R6F,链式依赖清晰。

### ✅ 执行体上下文预算(冷启动知识入口)
- [ ] 卡内**知识入口**指向的文档总量 < 执行体一次会话能消化的上限(约 50-100k tokens)。
- [ ] **精确制导**:只给执行本卡必读的最小文档子集,禁「读整个产品仓自己找」。
- [ ] **检查方法**:数一下卡内引用的文档/代码文件,累加行数,超 2000 行 → 必精简。
- [ ] **反例**:卡内写「知识入口:产品仓 ~/projects/lybra」→ executor 不知从哪读起,冷启动卡死。
- [ ] **正例**:卡内写「知识入口:tools/lybra-deploy(部署脚本)、tests/test_r6e_*.py(测试模板)」
  → executor 精确打击,10 分钟读完动手。

### ✅ 产品三问(避免方向跑偏)
出卡前问自己:
1. **What**(交付物是什么):本卡完成后,executor 交回的产出是什么?(代码、测试、文档、配置?)
2. **Why**(为什么现在做):这张卡解决什么具体痛点?不做会怎样?(用户撞墙?审计卡住?技术债?)
3. **How**(验收标准):怎么判断「做完了」?谁验收?用什么测试/检查点?(必须可执行、可重现)

- [ ] 三问都能一句话答清楚 → 可以出卡。
- [ ] 有一问答不清或答案模糊 → 先内部讨论澄清,再出卡。

## 出卡后:分发与执行

1. **分发**:卡文件 `5_tasks/queue/pending/<task_id>.md` 提交到治理仓;
   executor 冷启动时由 `/claim <卡>` 自动拉取。
2. **执行**:executor 只读卡 + 卡内知识入口,**不依赖任何历史上下文**(冷启动约束)。
3. **验收**:卡内 `artifact_scope` + 验收断言 = auditor 的唯一真相源;
   executor return 的交付清单必须与卡面对齐(缺项 = partial,差异结构化落 return 记录)。

## 常见反模式(禁止)

| 反模式 | 为什么禁 | 正确做法 |
|--------|---------|---------|
| 一卡塞 5 个不相关功能 | executor 无法原子交付,部分完成 = 审计噩梦 | 拆 5 张卡,各自独立验收 |
| 修复 + 验证混一卡 | 修复完 ≠ 验证通过,验收标准不清 | 修复卡 → 验证卡,后者依赖前者 |
| 知识入口 = 整个仓 | executor 冷启动读不完,token 耗尽 | 精确制导:只给必读的 2-3 个文件 |
| artifact_scope 写 6 个大项 | 范围爆炸,executor 无法在一会话完成 | 聚焦核心 1-2 项,其余另出卡 |
| 卡内没写验收标准 | auditor 不知道怎么判断「完成」 | 明确:通过哪些测试?改了哪些文件? |

## 本 skill 自身定位

- **目标读者**:advisor(顾问)出卡时自查用。
- **不是**:executor/auditor 的工作指南(他们只管执行/审已出好的卡)。
- **维护**:本 skill 随 LOOP-REDESIGN 设计权威演进;顾问发现新反模式时,补充到检查表。
- **分发**:由 tools/distribute_tools.py 按角色分发到顾问工位;executor/auditor 工位不装此 skill。
