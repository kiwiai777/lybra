# truth-first-drafting — 出卡先读真相(顾问铁律)

**为什么(Owner 2026-07-26 裁定)**:顾问 agent 的 memory 与会话记忆会随压缩失真;
项目复杂度越高,凭记忆出卡的漂移越大,且顾问漂移会放大到整串卡。**记忆≠真相**
(T5 的顾问版);治理文档才是真相(T6)。产品先例:copilot RF-5(每次起草前重读真相)。

## 规则

1. **出卡前必读**本项目治理真相入口(各项目在角色 AGENTS.md/CLAUDE.md 声明清单;
   lybra 项目 = direction_log 尾部近期条目 + roadmap 相关段 + 正典相关命题):
   与本卡相关的**约定、红线、既有裁定**必须以文档当前文本为准;
2. **卡内引用出处**:卡的方向依据处写明所读文档与条目(为将来 gate 的
   governance_refs 字段奠基——引用可审计,漂移可归因);
3. **memory 只作线索**:个人 memory/会话记忆用于"想起去查什么",不作为出卡依据;
   记忆与文档冲突时,**文档赢,且顺手修记忆**;
4. 治理入口读不到/版本存疑 → block-and-report 问 Owner,不凭印象补。

## 出卡前固化清单(六查——每张卡出手前逐项过,Owner 2026-07-27 裁定固化)

> 背景:项目复杂度上升后,顾问漂移的主形态是**局部思维**——只看眼前一张卡,
> 不看全局在途与接缝,导致整串卡互踩、项目受阻。以下六查全部来自真实事故。

1. **真相查**:上节规则 1(必读治理真相入口,以文档当前文本为准);
2. **全局查(反局部思维)**:盘点**在途卡清单、各角色车道、共享工作树状态**——
   本卡会碰谁的接口?谁的未 commit 改动会与本卡混树?出卡时就写明"在途排除项"
   (实案:253/254 混树 BLOCK、255 finalize 与 256 在途三文件的隔离条款);
3. **基线查**:基线 commit/环境状态**出卡时实测**,禁止从旧卡抄
   (实案:255FZ BLOCK-1,顾问抄了上一张卡的基线值);
4. **接缝查**:新机制必须回答"**它产出的东西能过既有的门吗**"——与既有协议/校验
   /状态机对拍(实案:253 派生卡过不了自家 claim 门 F-253-2、进不了判决链 F-253-4);
5. **六件套齐**:准绳、车道(精确 pathspec/排除项)、红线、**可独立取证的验收断言**
   (结构检查≠验收;实案:F-256R-3 两轮用注释顶替真 E2E)、落位、程序引用;
6. **出处入卡**:governance_refs 写明所读文档条目(规则 2)。

**六查非仪式**:每查对应一类已发生的漂移;跳查=把同类事故再买一次。
