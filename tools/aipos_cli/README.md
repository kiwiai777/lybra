# tools/aipos_cli — `lybra` 命令的实现

本目录是 `lybra` CLI 的 Python 实现。npm 入口 `bin/lybra` 委托到
`python3 -m tools.aipos_cli.aipos_cli`;源码检出时也可直接用模块入口。

**参数以 `lybra --help` / `lybra <子命令> --help` 为准**——本页只讲各命令在流程里的位置, 不复制参数表
(复制 = 第二源 = 漂移)。顾问侧的命令快查表随分发下发, 母本在
[`agents/skills/advisor-commands/SKILL.md`](../../agents/skills/advisor-commands/SKILL.md)。

## 现行流程里的命令

| 阶段 | 谁 | 命令 |
|---|---|---|
| 接入新项目 | 顾问(Owner 只敲向导标出的两步) | `lybra onboarding guide <项目名>` 打印该项目专属的全部步骤与失败出口;其中建项目 = `lybra project new`, 声明产品仓 = `lybra project set-repos`(写 project.json 的 `set-repo` / `set-repos` / `set-paths` / `set-workstation` / `set-meta` 同一两阶段:缺省预演, 打印将写的 project.json diff 与校验结果、零写入;`--confirm` 才写, 写后即经治理提交口落账(AIPOS-F159);输出首行写明目标项目、来源与 project.json 绝对路径。目标项目 = 显式项目名 > `--workspace-root` / 当前目录所在治理根的 project.json#project > 拒, 绝不回落 home 级活动项目;显式项目名与所在治理根不一致 = 拒并列出两者;`freeze-legacy`、`dispatch-mode set` 同一解析。`set-meta --phase/--note` 写 project.json 说明键, 键须先在 config.schema project_json 声明);逐步自检 `lybra onboarding check`。顾问会话 harness:`--advisor-harness` 取值读 `distribution.schema` `harness_semantics.kinds`(`advisor_session=true` 的 kind, 缺省 `claude-code` = 既有向导);`codex` = Codex 会话(可在他机, `--advisor-host` 给会话所在机, 其短名作顾问实例名 host 段, 不默认成治理根所在机)——第 4 步写 `lybra roles enroll-deliver … --harness codex [--harness-dir] [--harness-host]`(Owner 在治理根所在机运行, 码不出进程), 凭据落治理根 `.lybra/`, role 如实记 `{kind, dir, host}`, 不建 `.pi` 接线、不分发 `.claude/skills`(声明无 codex 件) |
| 出卡 / 改卡 | 顾问 | `lybra draft create` → `lybra draft publish`;`lybra queue amend` / `withdraw` / `rework`。返工(审计 FAIL 后追加返工节)由顾问以自己的实例签发:`lybra queue rework --task-id <卡ID> --actor <顾问实例> --verdict-ref <裁决记录ID> --focus-items '["…"]' --acceptance-criteria '["…"]' --confirm`(不带 `--confirm` = 预演: 显示将追加的返工节并预检签发实例, 零写入不调门, AIPOS-F155;登记后 `lybra loop` 等执行体按返工节修复重交, 再自动派下一轮审计)——`--actor` 即签发实例, 按该实例在治理根 `.lybra/connection.json` 的凭据签并作为 `agent_instance` 交门, 未接入本治理根的实例即拒(列出已接入实例), 从不取连接文件里第一个顾问凭据;`queue adopt --actor` 同此(两者同一口 `two_phase_shell_factory.signer_role_for_actor`)。其余按角色取凭据的薄壳在同一角色有两个及以上实例时拒(须经 `lybra loop --actor <实例>` 或设 `LYBRA_DRIVER_INSTANCE`) |
| Owner 中途改了在途卡的目标(AIPOS-F184) | 顾问(转达 Owner 原话) | 先按新目标出新卡并发布(`lybra draft create` → `lybra draft publish`), 再撤换原卡:`lybra queue supersede --task-id <原卡> --by <新卡> --actor <你的顾问实例> --owner-words <Owner 原话摘要> [--owner-ref <收件箱事项ID|裁决记录ID>]`(缺省预演零写入;`--confirm` 写入:Owner 原话落 owner_decision_record(与 `owner decide --relayed-by` 同一记录类型)→ 原卡 pending / claimed / blocked 均可置 withdrawn 终态, 卡面记 `superseded_by` 与 Owner 原话 → 写出文件自动落账;Owner 收件箱该卡的待决事项随之消失;原卡工作树与卡分支保留由结案清理处理)。不须执行体身份, 不受撤回的 24h 在途会话保护;`--actor` 须是顾问角色类实例, 新卡须已在队列。**不要再以执行体身份 `queue block` 原卡再重出卡**(原卡会留在收件箱要 Owner 再定一次)。声明 `transitions.schema` `queue_mutations.transitions.supersede` / `verbs.schema` `lybra_queue_supersede` |
| 顾问起草的在途卡契约需更正 / Owner 改目标但原卡已做工作要保留(AIPOS-F186) | 顾问 | 出更正卡并发布 → `lybra queue supersede --task-id <原卡> --by <新卡> --actor <你的顾问实例> --owner-words <Owner 原话摘要> --carry-branch`(缺省预演零写入, 列原卡分支名 / tip / 工作树路径 / 未提交改动计数;`--confirm` 写入:决策记录 → 新卡卡面记 `carried_from {task_id, branch, tip}`(经 `queue amend` 同一实现, 修订记录随同落账)→ 原卡 withdrawn)→ 跑新卡 loop:认领时新卡分支从原卡分支 tip 建(原卡分支保留), 认领输出「承继自 <原卡> <分支>@<tip>」, my-tasks / card render 显示承继来源并提示先合入当前 main。拒:原卡工作树有未提交改动(产品不代提交, 先让执行体在原卡分支提交)/ 原卡无卡分支 / 新卡非 pending 或已认领 / 新卡卡分支已存在;认领时原卡分支 tip 与记录不符 = 拒认领(CARRY_TIP_MOVED)。审计与合入差异基线仍按 main(承继提交一并审;交回车道检查同口径, 更正卡 lane.paths 须覆盖原卡已改的路径), 结案记录写 `carried_from`。声明 `transitions.schema` `queue_mutations.transitions.supersede.carry_branch` / `card.schema` `carried_from` |
| 外部项目合入交给 Lybra(`finalize_mode` 切 `internal`) | 顾问(声明写入经 Owner 两阶段确认) | 适用于人肉期接入、原由外部 FINALIZE 卡合入的项目(任何项目同一组命令, 不写死项目/卡号)。**前置**:① 产品仓在治理根所在机、已用 `lybra project set-repos <项目> --repo <仓名>=<绝对路径> …` 声明, 卡 `lane.repo` 写仓名;② 各产品仓工作树在 `main` 且干净(脏树 finalize 拒并列脏文件);③ 在途 PASS 待合入卡先合完或确认无(外部模式下同仓推导已互斥, 见下)。**步骤**:① 不部署的仓随 set-repos 一并声明 `--no-deploy <仓名>`(可重复;set-repos 为整段声明, 未给即清空, 预演 diff 可见)→ finalize 不调部署脚本, finalization 记录 `deploy_status=not_applicable` 并写依据;② `lybra project set-paths <项目> --key finalize_mode --value internal` 预演后 `--confirm`;**既有项目声明阶段档案位置**(AIPOS-F145):项目阶段档案(阶段快照)不在缺省 `<治理根>/stage_archive/`(如人肉期放在 `governance/stage_archives/`)时, 同一写入口 `lybra project set-paths <项目> --key stage_archive_root --value <相对治理根路径>` 预演后 `--confirm`——finalize 阶段闸门、brief、governance-commit、close 鲜度检查与 `governance add stage` 都按此落点(唯一读取口 `workspace_config.stage_archive_root`), 未声明 = 缺省落点, 落点下无快照 = 阶段闸门拒并附同一出口;③ 之后 `lybra loop` 在 N4 PASS 后派生 `lybra finalize`(在本机合并)。**推送**:仓无 origin 远端或无 `origin/<基线>` = 推送不适用, 结果与 finalization 记录如实标 `push_status=not_applicable`(其余值 `pushed` / `already_synced` / `not_requested`, 声明 `transitions.schema` N5.record.push_status)。**同仓串行**:同一产品仓同时只合一张——内部 finalize 合并前取仓级锁(产品仓 git common-dir 下 `lybra-finalize.lock`, 工作树共享), 另一张在途即 BLOCK `REPO_MERGE_IN_PROGRESS`(点名持锁卡, 可重试);外部模式推导对同仓后到的 PASS 卡返回 `await_repo_turn`(不派 FINALIZE, loop 等先合入卡的 finalization 记录) |
| 派子 agent 的开工稿(AIPOS-F187) | 顾问 | `lybra kickoff --task-id <卡ID> [--role executor\|auditor] [--json]`:输出一份可直接交给子 agent 的自足开工稿(身份实例、章程命令、卡面路径、工作树 / 分支 / 基于哪个 main sha、承继来源、报告落点与 frontmatter 必填字段、写权限边界与禁写清单、硬规矩、草稿目录、验证要求、交回前残留进程检查、写完即止、末尾简短总结), 顾问原样交给子 agent 并可在其后追加本卡特别说明——**不再手写开工稿**。只读(不写文件、不连门、不起进程)。开工稿是渲染: 骨架与句子只在 `verbs.schema` `lybra_kickoff`, 值取卡面 + project.json(`repos`、`paths.scratch_root`、`test_contract.runall_path / ratchet / residual_processes`)+ 章程既有单源(`roles.schema` `write_boundary`、`paths.hard_rules_source` § 0.5)。可开工判据与工位 `/go` 同一(`next_resolver.kickoff_refusal`)。草稿目录 = `paths.scratch_root/<卡ID>`(`lybra project set-paths --key scratch_root`; 未声明 = 系统临时目录, 落治理根内 = 拒)。子 agent 会话在他机(如 chris Codex 顾问)= 章程命令给 ssh 拉取式并注明路径在治理根所在机。loop 子 agent 模式的等待提示与 `loop status` 下一动作指向本命令 |
